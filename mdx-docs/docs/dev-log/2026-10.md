## Local models + Rust offline, before a flight — 17 October

right so.... trying to get local models and a Rust setup ready before a flight. should be fairly boring. download the things while i have internet, use them when i don't.

what am I trying to understand here? why does everything look like it's working but either run slowly or need a machine somewhere else?

four separate things giving me the same sort of lie. the default package used the central processing unit (CPU), the upgrade went back to it, the model loader let the rebuild succeed without the models, and opencode's "local" provider was my work desktop. each one looked enough like the previous problem to send me round again. plus an old package pin and a tmux indicator that couldn't see this hardware anyway...

the laptop is `degen-home`. AMD (Advanced Micro Devices) Ryzen AI (artificial intelligence) 9 365, Radeon 880M integrated graphics processing unit (GPU), 30GB of random access memory (RAM). no discrete GPU hiding in here. the LLVM compiler target (originally Low Level Virtual Machine) is `gfx1150`.

the GPU exposes 15.7GB through GTT (Graphics Translation Table). that's the slice of system RAM it can address. not another 15.7GB of memory i magically own.

first problem was just the nix default. all i had was:

```nix
services.ollama.enable = true;
```

which enables ollama. says nothing about using the GPU. the module's `package` defaults to `pkgs.ollama`, which resolves to `ollama-cpu` unless `nixpkgs.config.rocmSupport` or `nixpkgs.config.cudaSupport` is set. those select ROCm (Radeon Open Compute) or CUDA (Compute Unified Device Architecture) support.

the log had `total_vram="0 B"` and `library=cpu`. VRAM is video RAM. fairly unambiguous once i actually looked at it.

ROCm doesn't support `gfx1150` properly. `rocminfo` returned nothing. RADV (Radeon Vulkan), Mesa's open source AMD Vulkan driver, was already present, so Vulkan it is:

```nix
services.ollama.package = pkgs-unstable.ollama-vulkan;
```

also the old `services.ollama.acceleration` option is REMOVED. not deprecated in the helpful sense. it errors and tells me to set `package` instead.

then the models wouldn't pull. `gpt-oss:20b` and `qwen3.6:35b-a3b` both hit:

```text
412: The model you are attempting to pull requires a newer version of Ollama
```

the `nixos-26.05` pin had ollama 0.24.0. updating the `nixpkgs-unstable` input with `nix flake update` took it to 0.40.3. i didn't need to add another input or invent plumbing for it. `nixpkgs-unstable` was ALREADY there, and `pkgs-unstable` was already passed to every host through `specialArgs`. `streaming-server/immich.nix` was the existing example. should have looked there first.

ok so newer ollama, Vulkan package, done?

no. the GPU stopped being used again.

this is the annoying one. newer ollama drops integrated GPUs unless `OLLAMA_IGPU_ENABLE=1` is set. iGPU just means integrated GPU. older builds ignored that flag on the Vulkan backend; newer ones enforce it. so i fixed the package, it worked, upgraded to get the models, and silently un-fixed the GPU.

the log actually told me at 08:46:

```text
level=INFO source=runner.go:405
msg="dropping integrated GPU; to enable, set OLLAMA_IGPU_ENABLE=1"
```

i missed that for about THREE HOURS.

why? i was grepping for `error|fail|vulkan|offload`. the keyword here is "dropping". the level is `INFO`. ollama logs decisions at INFO, including the decision to stop using the hardware i'm trying to debug. no error required, it can still run on the CPU...

and `OLLAMA_IGPU_ENABLE` wasn't in the official GPU docs at `docs.ollama.com/gpu`. found it by running `strings` on the binary. the ArchWiki documents it. apparently reading the executable was part of setting up the laptop today.

setting `OLLAMA_IGPU_ENABLE=1` got the GPU back. keeping the three package/backend problems separate, because they all ended up looking like "ollama is slow":

meanwhile tmux said "No GPU" through all of this. which looked like confirmation of the other problems. unrelated.

tmux-cpu's detection is literally `if command_exists nvidia-smi ... else echo "No GPU"`. no AMD path at all. patched it to fall back to amdgpu's sysfs entries, the kernel's filesystem interface for device information.

first attempt hardcoded `card0`. still "No GPU". this machine is `card1`. now it globs `/sys/class/drm/card*/` instead. DRM here is Direct Rendering Manager.

it reports GTT rather than VRAM. the nominal VRAM is 512MB, which is meaningless for this job. the weights actually land in GTT. one caveat for future me: tmux-cpu is a plain git checkout in `~/.config/tmux/plugins`. a plugin update wipes this patch.

the Rust bit was much less dramatic.

`rustc` and `cargo` 1.95.0 from nixpkgs. the `wasm32-unknown-unknown` standard library for WebAssembly (wasm) is ALREADY inside the rustc derivation. no `rustup target add` needed.

the stack is axum for the server, Leptos for the wasm client, no JavaScript authored. `mp4` and `matroska` crates for container parsing, pure Rust, no ffmpeg C dependency.

#21 ownership again....
going to try and draw up a table of my understanding of ownership...

| concept | minimal example | explanation |
|---|---|---|
| copying | `fn add_1(val: u32)` | value is copied (`i32` is copyable) and immutable |
| copying | `fn add_1(mut val: u32)` | copied again, `fn` can change but no effect on caller var |
| move | `fn add_val(vec: Vec<i32>)` | vector does NOT implement copy, so `fn` now OWNS the vec, parent vec lost |
| move | `fn add_val(mut vec: Vec<i32>)` | same as above `fn` takes ownership, but now can change its values |
| refs | `fn add_val(myvec: &Vec<i32>)` | immutable reference (borrowing), so no ownership change |
