## systemd rules
right so under `systemd [Unit]`

- `wants/requires` is should the unit actually be run?
- so `A wants B` means A ... needs B to run, but can be started concurrently (along for the ride)
- `A wants B` is more like if A started, start B, A wont fail if B failes
- `A wants=B After=B` means needs B and should run after B has started
- `wantedby` is the reverse of `wants`, i.e. `network-manager wantedBy=tailscale`, as tailsacle will need networkmanagewr

ahhhhh so
- `A requires=B` means `A wants=B` but unlike `wants` if B fails A also fails

right table from codex explaining... for the "starting" relationships, i.e. when units should be switched on or not
| Forward | Reverse | Explanation |
|---|---|---|
| `Wants=B` | `WantedBy=A` | Starting A also requests B. B may fail; A continues. |
| `Requires=B` | `RequiredBy=A` | Starting A also requests B. Stronger failure/stop coupling. |
| `BindsTo=B` | `BoundBy=A` | Like `Requires`, but A also stops if B disappears/crashes. |
| `PartOf=B` | `ConsistsOf=A` | Stopping/restarting B also stops/restarts A. |
| `Requisite=B` | `RequisiteOf=A` | B must already be active; does not start B. |

> according to codex, a for `A Requires=B`. on start by `B` means `A` does not start, but later on if `B` crashes `A` will NOT stop

not 100% sure about `bindsTo` and `partOf` honestly

then for ordering

| Forward | Reverse | Explanation |
|---|---|---|
| `After=B` | `Before=A` | If both start, wait for B before starting A. |

## image trimming
So the purpose of this is to try and bring down the size of the container to save on space when I want to spin up a test?

But a few points to clarify which I seem to be getting confused with
1. doing `pacman -S gdu` inside `Dockerfile` is NOT the same as doing it in a container
    - both install files on disk: the first in an image layer, the second in the container's writable layer
    - running the installer or scanning files can increase RAM usage, including caches that can remain afterwards and be reclaimed when needed
2. docker image layers stay on disk; files are loaded into RAM as programs use them, not all at container startup

however, trimming down the absolutely necessary neovim dependencies and keybindings to allow me to keep the container RAM small simpy because it won't be spamming language servers
